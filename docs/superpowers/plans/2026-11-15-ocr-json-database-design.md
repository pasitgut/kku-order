# แผน Implement: เก็บผล OCR ใน JSON และบันทึกข้อมูลเมื่อผู้ใช้เลือก

> อัปเดต: ผู้ใช้ยืนยันว่าข้อมูลเดิมยังไม่ใช้งานจริงและอนุญาตให้ลบตารางเก่าแล้ว แผนส่วนที่กล่าวถึงตาราง legacy และการย้ายข้อมูลเดิมถูกแทนที่ด้วย baseline ใหม่สำหรับฐานข้อมูลว่าง

## เป้าหมายและขอบเขต

ผลประมวลผลที่ยังไม่บันทึกฉบับร่างหรือยืนยันอยู่ในไฟล์ JSON ส่วนข้อมูลที่ผู้ใช้บันทึกแล้วอยู่ในฐานข้อมูล ผล OCR ยังคงเก็บเป็นไฟล์เพื่อแสดงหลักฐานต้นฉบับหลังบันทึก ห้ามเปลี่ยนโค้ดหรือข้อมูลตามเอกสารนี้จนกว่าจะเริ่มงาน implement

DB ยังต้องมีระเบียนเอกสารตั้งแต่นำเข้า เพื่อเก็บ ID, ที่อยู่ไฟล์ต้นฉบับ, hash, สถานะ, คิว, ข้อผิดพลาด และตำแหน่ง JSON ข้อมูลดังกล่าวเป็นข้อมูลควบคุมระบบ ไม่ใช่ข้อมูลคำสั่งที่ผู้ใช้บันทึก

แผนนี้ครอบคลุม PDF และผลนำเข้า DOCX/XLSX/CSV ซึ่งปัจจุบันใช้เส้นทางบันทึกผลร่วมกัน การรวมตาราง `documents`, `orders` และตารางกรรมการเป็นงาน DB อีกชุด ให้ทำภายหลังแยกจากการย้าย OCR เพื่อลดความเสี่ยง

## สถานะปัจจุบัน

- `backend/extractor_http.go` อ่าน JSON จาก HTTP response และแปลงเป็น `ExtractionResult` ไม่ได้เก็บ response เป็นไฟล์ถาวร ส่วน `import.json` ใน `backend/document_processing.go` เป็นไฟล์ชั่วคราว
- `backend/document_queue_store.go` บันทึกผลสกัด, appointments, references, OCR pages และ lines ลง DB ทันที แล้ว sync ตาราง core
- `GET /api/v1/documents/:id` โหลด `OCRPages.Lines` ใน `backend/main.go`; หน้าตรวจสอบใช้กรอบและขนาดหน้าใน `src/components/document-workspace.tsx`
- การค้นหาข้อความเต็มใช้ `document_workflows.ocr_text` ใน `backend/api_handlers.go` รายงานและการค้นหาบุคคลอ่านข้อมูลจาก DB
- ปุ่มบันทึกและยืนยันในปัจจุบันเรียก update แล้ว confirm แยกกัน และระบบรองรับยืนยันอัตโนมัติ

## กติกาข้อมูล

| ขั้นตอน | แหล่งข้อมูลที่แสดง | สิ่งที่เขียน DB |
| --- | --- | --- |
| นำเข้าและกำลังประมวลผล | ไฟล์ต้นฉบับ | ข้อมูลควบคุมเอกสารและคิว |
| ประมวลผลเสร็จ ยังไม่บันทึก | ผลสกัดใน JSON | สถานะ, ผลสำเร็จหรือข้อผิดพลาด, ที่อยู่และรุ่น JSON |
| บันทึกฉบับร่าง | ข้อมูลฉบับร่างใน DB; OCR จาก JSON | ข้อมูลคำสั่ง, fields, appointments และ references ทั้งชุด พร้อมสถานะฉบับร่าง |
| ยืนยัน | ข้อมูลที่ยืนยันใน DB; OCR จาก JSON | ข้อมูลทั้งชุด สถานะ ผู้ยืนยัน เวลา และ audit ใน transaction เดียว |

ให้ระบุแหล่งข้อมูลด้วยตัวบ่งชี้แยก เช่น `content_state` ค่า `UNSAVED`, `DRAFT`, `CONFIRMED` หรือเทียบเท่าที่ชัดเจน อย่าใช้ `NEEDS_REVIEW` ตัดสินว่าเคยบันทึกหรือไม่ เพราะสถานะเดิมใช้ทั้งสองกรณี รักษาความหมายของสถานะงานเดิม รวมถึง `RETURNED`, การยกเลิก และสถานะ processing ให้ชัดเจน การส่งกลับเอกสารที่ยืนยันแล้วต้องยังอ่านข้อมูลที่บันทึกใน DB ได้

ก่อนบันทึก ผู้ใช้แก้ข้อมูลใน browser ได้ แต่การแก้ไขที่ยังไม่กดบันทึกอาจสูญหายเมื่อปิดหรือรีเฟรชหน้า บันทึกฉบับร่างต้องบันทึกข้อมูลทั้งชุด แม้ไม่มีการแก้ไขจากผล OCR

## รูปแบบและการจัดเก็บ JSON

ใช้ JSON กลางที่มี version อย่างน้อยประกอบด้วย document ID, รุ่นผลประมวลผล, engine, ผล `ExtractionResult` และผลสกัดพร้อมแสดงที่ผ่าน `buildExtractionRecords` รวมถึง fields, appointments, references และค่า metadata ที่หน้าจอต้องใช้ เก็บตำแหน่งหน้า ขนาดภาพ กรอบข้อความ ความมั่นใจ และลำดับให้ครบ ผลสกัดพร้อมแสดงต้องผ่านการจับคู่บุคคลและตำแหน่งเช่นเดียวกับปัจจุบัน โดยไม่ถือว่าการจับคู่คือการยืนยันของผู้ใช้

`ExtractionResult` เป็นผลกลางหลัง adapter แปลงแล้ว ไม่จำเป็นต้องเหมือน JSON ดิบจากผู้ให้บริการ และอาจไม่มีข้อมูล provider ทั้งหมด หากต้องเก็บ response ดิบเพิ่มเติม ให้ตัดสินใจแยกตามความจำเป็น อย่าสมมติว่าสามารถสร้าง response ดิบกลับจากผลกลางได้

จัดเก็บไฟล์ในพื้นที่ถาวรที่ backend เข้าถึงได้และสำรองพร้อม DB ใช้ชื่อจาก ID และรุ่นที่ระบบสร้าง ไม่ใช้ชื่อไฟล์จากผู้ใช้ สร้างไฟล์ชั่วคราวใน filesystem เดียวกัน ตรวจ JSON และเขียนให้ครบก่อน rename เป็นไฟล์รุ่นใหม่ จากนั้นจึงบันทึก pointer และสถานะใน DB โดยตรวจรุ่นงานและล็อกระเบียนเอกสาร หากขั้นตอน DB ล้มเหลว ไฟล์ใหม่ถือเป็น orphan และเก็บกวาดภายหลังได้ ห้ามลบไฟล์รุ่นเดิมก่อน pointer ใหม่ commit แล้ว

หากไฟล์หาย เสีย อ่านไม่ได้ หรือ version ไม่รองรับ ให้ API แจ้งข้อผิดพลาดที่ตรวจสอบได้ และไม่แสดงข้อมูลว่างเหมือนสำเร็จ ไม่สร้าง JSON เปล่าแทนข้อมูลที่หาย กำหนดสิทธิ์อ่านและ backup ให้เทียบเท่าเอกสารต้นฉบับ เพราะ JSON อาจมีข้อมูลส่วนบุคคล

## ขั้นตอน implement

### 1. เตรียม schema และ storage แบบเข้ากันได้

- เพิ่ม migration ใหม่สำหรับ pointer/version ของ JSON และตัวบ่งชี้ว่าข้อมูลเนื้อหาอยู่ใน DB แล้ว ห้ามแก้ migration ที่เคยรัน
- คงตารางและคอลัมน์เดิมในช่วงเปลี่ยนผ่าน ตรวจข้อจำกัด schema ปัจจุบันโดยเฉพาะ `documents.id` ที่อ้าง `orders.document_id` และการสร้าง `PENDING`; อย่าลบจนกว่าจะปรับผู้เรียกทั้งหมด
- เพิ่มตัวอ่าน/เขียนไฟล์และ validation พร้อมการจัดการข้อผิดพลาด โดยใช้ผล `ExtractionResult` กลางสำหรับทุก adapter และ structured import

### 2. เปลี่ยนการประมวลผลและการอ่าน

- หลัง OCR สำเร็จ สร้าง JSON พร้อมผลสกัดและจับคู่ แล้วอัปเดตสถานะ/ตำแหน่งไฟล์เท่านั้น ไม่สร้าง fields หรือ appointments ใน DB สำหรับเอกสารใหม่ที่ยังไม่บันทึก
- ปรับ `GET /api/v1/documents/:id` ให้สร้าง response รูปแบบเดิมจาก JSON เมื่อ `UNSAVED` และจาก DB เมื่อเป็น `DRAFT`/`CONFIRMED`; OCR pages/lines อ่านจาก JSON ในทุกสถานะ
- กำหนด ID ชั่วคราวที่คงที่ภายใน JSON หนึ่งรุ่นสำหรับ fields และ appointments เพื่อให้ UI แก้ไขและลบแถวได้ หลังบันทึกให้ response ส่ง ID จริงจาก DB แล้วแทน state ฝั่ง UI
- รักษาการแสดงขนาดหน้า bounding box ข้อความ OCR และ preview สำหรับไฟล์ที่ไม่ใช่ PDF

### 3. บันทึกร่างและยืนยัน

- รับข้อมูลทั้งชุดจากหน้าจอ ตรวจสิทธิ์และ validation รวมทั้งความสัมพันธ์บุคคล ป้องกันการอ้าง ID จากเอกสารอื่น
- ล็อกเอกสาร ตรวจรุ่น JSON/รุ่นข้อมูลที่หน้าจอเปิดอยู่ ปฏิเสธการเขียนทับข้อมูลที่ใหม่กว่า แล้วบันทึกข้อมูลทั้งชุดและ audit ใน transaction เดียว
- ปรับการบันทึกและยืนยันให้เป็น operation เดียวใน transaction เดียว รวมการตรวจเงื่อนไขยืนยันและข้อมูลผู้ยืนยัน หาก validation หรือการเขียนล้มเหลว ห้ามเหลือเอกสารที่ยืนยันเพียงบางส่วน
- ปรับ auto-confirm ให้อ่านและตรวจผลสกัดที่ยังไม่บันทึก แล้วนำข้อมูลลง DB พร้อมยืนยันใน transaction เดียว ตามการตั้งค่าเดิม ต้องรักษาเกณฑ์และการจับคู่เดิม

### 4. ค้นหาและรายงาน

- ผู้ใช้กำหนดให้ค้นเลขคำสั่ง รายชื่อ และข้อความ OCR ได้ก่อนบันทึก โดยห้ามเก็บเนื้อหาก่อนบันทึกใน DB แม้เป็นดัชนีชั่วคราว ดัชนีจึงต้องอยู่นอก DB และสร้างใหม่จาก JSON ได้
- ผสานผลค้นหาจากดัชนีภายนอกกับข้อมูลใน DB ก่อนนับจำนวน กรอง เรียงลำดับ และแบ่งหน้า ตรวจผลกับการค้นหาเดิม รวมถึงตัวกรองและคำค้นภาษาไทย ห้ามสแกน JSON ทุกไฟล์ต่อคำค้นโดยไม่วัดประสิทธิภาพ
- หลังบันทึก ให้ค้น fields และ appointments ตามเดิม ส่วนข้อความ OCR ยังค้นจากดัชนีภายนอก กำหนดวิธีอัปเดตเมื่อมี JSON รุ่นใหม่และลบเมื่อเอกสารถูกลบ หากดัชนีไม่พร้อมต้องแจ้งข้อผิดพลาด ไม่คืนผลที่ขาดไปเหมือนค้นหาสำเร็จ

### 5. ประมวลผลซ้ำ อัปโหลดทับ และลบ

- ผลใหม่เป็น JSON รุ่นใหม่ ห้าม worker เก่าหรือเอกสารที่ถูกยกเลิกเขียนทับ pointer รุ่นปัจจุบัน
- หากมี draft หรือข้อมูลยืนยันแล้ว ให้คงข้อมูล DB เดิมและงานที่ผู้ใช้เพิ่มไว้ รวม `extra_duties` จนผู้ใช้เลือกนำผลใหม่มาใช้และบันทึก ไม่แทนข้อมูลที่บันทึกเพียงเพราะ OCR เสร็จ แสดงให้ชัดว่าผลใหม่ยังไม่ถูกบันทึก
- กำหนดสถานะระหว่างสแกนและหลังสแกน: สั่งสแกนซ้ำแล้วเอกสารออกจากสถานะยืนยัน (`PROCESSING` แล้วกลับมารอตรวจ) แต่ยังเก็บ `confirmed_by`/`confirmed_at` เดิมไว้ จนผู้ใช้เลือกนำผลใหม่มาบันทึกจึงล้าง ส่วนอัปโหลดทับล้างข้อมูลผู้ยืนยันทันที (ตามโค้ดหลัง commit c040085) ระบุให้ชัดว่ารายงาน/การแจ้งเตือนยังไม่รวมเอกสารจนยืนยันใหม่ กรณีงานล้มเหลว ข้อมูลเดิมต้องกู้ดูได้
- ลบเอกสารแล้วจัดการไฟล์ JSON ทุก revision เช่นเดียวกับไฟล์ต้นฉบับ รายงานความล้มเหลวในการลบและมีวิธีเก็บกวาดไฟล์ค้าง ห้ามลบก่อน DB commit โดยไม่มีทางกู้คืน

### 6. ย้ายข้อมูลเดิมและลด schema

- สำรอง DB และไฟล์ต้นฉบับ ทดลองกู้คืนก่อน เริ่มด้วยการสำรวจจำนวนเอกสาร สถานะ OCR และความแตกต่างระหว่างตาราง รวมทั้งผู้ใช้หรือระบบที่อ่าน DB ตรง
- สร้าง JSON จาก OCR pages/lines และข้อมูลที่มีอยู่สำหรับเอกสารเก่า แล้วตรวจจำนวนหน้า บรรทัด ข้อความ กรอบ และความสามารถเปิดเอกสารเทียบก่อนย้าย ไฟล์ที่สร้างจาก DB เป็นข้อมูลที่สร้างย้อนกลับ ไม่ใช่ response ดิบเดิม
- อย่าสมมติว่าสถานะ `NEEDS_REVIEW` หมายถึงไม่เคยบันทึก จำแนกจากหลักฐาน audit/revisions หากพิสูจน์ไม่ได้ ให้ถือว่าข้อมูลใน DB เป็นข้อมูลที่บันทึกแล้วและคงไว้ แจ้งจำนวนกรณีที่จำแนกไม่ได้
- ใช้ migration แบบเพิ่มก่อน ย้ายและตรวจสอบ แล้วสลับการอ่าน หลังผ่านการตรวจจึงแยก migration ภายหลังเพื่อลบ `ocr_pages`, `ocr_lines` และสำเนาข้อความที่ไม่จำเป็น รวมถึง model, callers และ tests ที่เกี่ยวข้อง ตัด `ocr_text` ได้ต่อเมื่อมีทางทดแทนการค้นหาหรือยอมรับการเปลี่ยนพฤติกรรมแล้ว
- rollback ระหว่างเปลี่ยนผ่านต้องรองรับข้อมูลใหม่ที่เกิดหลังสลับการอ่าน: เก็บ JSON และ DB ไว้ สร้างข้อมูลกลับไปยังรูปแบบเดิมก่อนสลับโค้ดกลับ ทดสอบ rollback บนสำเนาที่มีการเขียนข้อมูลหลัง migration แล้ว ห้ามพึ่งการ restore backup อย่างเดียวเพราะอาจสูญเสียข้อมูลใหม่

## เกณฑ์ตรวจรับ

- [ ] นำเข้า PDF และ DOCX/XLSX/CSV ได้ ผล OCR/สกัดอยู่ใน JSON และไม่มี fields/appointments ที่ยังไม่บันทึกใน DB
- [ ] เปิดเอกสารก่อนบันทึก แสดงข้อมูล กรอบ ขนาดหน้า และ preview ได้ตรงกับผลเดิม รวมกรณีไม่พบไฟล์หรือไฟล์เสีย
- [ ] บันทึกร่างโดยไม่แก้ไขและโดยเพิ่ม/แก้/ลบแถว แล้วเปิดใหม่ได้ครบ พร้อม ID จริง; ผู้ใช้สองคนแก้พร้อมกันแล้วไม่เขียนทับกันเงียบ ๆ
- [ ] บันทึกและยืนยัน รวมถึง auto-confirm สำเร็จแบบ atomic; เมื่อเกิดข้อผิดพลาดไม่มีข้อมูลยืนยันบางส่วน
- [ ] ส่งกลับ ยกเลิก สแกนซ้ำ อัปโหลดทับ และงานล้มเหลว ไม่ทำข้อมูลผู้ใช้สูญหาย และรายงาน/แจ้งเตือนตรงสถานะ
- [ ] ทดสอบการค้นหาและรายงานตามขอบเขตที่ตกลง รวมข้อมูลที่ยังไม่บันทึก และข้อความ OCR
- [ ] ย้ายข้อมูลเก่าแล้วเทียบจำนวนและเนื้อหา ตรวจกรณีจำแนก draft ไม่ได้ และทดสอบ backup/restore รวม JSON กับ DB
- [ ] ทดสอบไฟล์เขียนไม่สำเร็จ DB commit ไม่สำเร็จ worker ซ้ำ การลบไฟล์ไม่สำเร็จ และ rollback หลังมีข้อมูลใหม่
- [ ] ทดสอบสิทธิ์เข้าถึง JSON และไม่เปิดเผยข้อมูลผ่าน path หรือ API โดยไม่ได้รับอนุญาต

## การตัดสินใจก่อนลงมือ

1. ผู้ใช้เลือกให้ค้นหาข้อมูลก่อนบันทึกได้ โดยไม่เก็บเนื้อหาหรือดัชนีใน DB ก่อนบันทึก
2. ผู้ใช้เลือกให้เก็บข้อมูลเดิมเมื่อสแกนซ้ำ และให้ผู้ใช้เลือกนำผลใหม่มาใช้
3. ไม่มีฐานข้อมูล MySQL ทดสอบแยก จึงให้รันทดสอบที่ไม่ต้องเชื่อมฐานข้อมูลก่อน การทดสอบ migration และ transaction กับ MySQL ยังเป็นข้อจำกัด
4. ตรวจการ deploy ว่าพื้นที่เก็บไฟล์ถาวร ใช้ร่วมกันได้ทุก instance และมี backup/restore ก่อนกำหนด path จริง
